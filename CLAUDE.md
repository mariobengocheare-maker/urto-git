# URTO — Ultimate Realtor Tool

Solo-user local tool for a Miami-Dade real estate agent (Mario Bengochea). Flask + vanilla HTML/CSS/JS — **no build step, no npm install, no React/Tailwind/TypeScript**. Runs as `python app.py`, opened at `http://localhost:5000` on the user's own Windows PC.

33. Mario shared a real results CSV (60 rows: 34 FOUND / 14 SKIPPED / 12 NOT_FOUND) asking to analyze the misses. Two were genuine parsing bugs, now fixed: (1) `llc_lookup._split_person_name()` only handled Sunbiz's `"LAST, FIRST"` comma convention — a registered agent with a generational suffix is often listed as a THIRD comma segment, `"LAST, SUFFIX, FIRST"` (e.g. `"HACKETT, II, JOHN"`), which the old first-comma-only split mangled into a garbage name (`"Ii, Hackett"`, `owner` field literally containing a stray comma). ## Architecture

- `app.py` — Flask app. Owns Skip Trace/Owner Lookup's own routes directly (lookup jobs, heartbeat/shutdown/version). Every CRM/Dialer/Transactions/Calendar route is instead forwarded to the hosted server via `hosted_sync.py` — see build order #71 — desktop has no local CRM database of its own anymore.
- `hosted_sync.py` — desktop's half of "one cloud": a generic proxy that forwards every `/api/crm`, `/api/backup`, `/api/txn`, `/api/text_presets` request to whatever hosted URL Mario configured (`/hosted_setup`, one-time), reusing a logged-in session cookie. If a future route is added to `crm_routes.py` under one of those four prefixes, it works on desktop automatically with zero changes here — only add to `PROXY_PREFIXES` if an entirely NEW prefix is ever introduced.
- `launch_desktop.pyw` — Windows double-click entry point (see build order #16). Checks if the server's already up on `127.0.0.1:5000`; if not, spawns `app.py` detached/hidden via `sys.executable` (which is `pythonw.exe` when this `.pyw` itself was launched that way — no console window at any point), waits for it to come up, then opens the browser. Re-launching while already running just opens another browser tab instead of a second server.
- `Create URTO Desktop Icon.vbs` — one-time setup Mario double-clicks to create the "URTO" Desktop shortcut pointing at `launch_desktop.pyw`, with `static/urto_icon.ico` as its icon. Resolves its own folder via `WScript.ScriptFullName` (not the shell's current directory, which isn't reliable for a double-clicked script), so it works regardless of where the project folder lives.
- `static/urto_icon.ico` — the desktop shortcut's custom icon (see build order #17).
- `urto_updater.pyw` — one-click self-updater (see build order #36). Downloads the latest branch ZIP from GitHub, stops any running `app.py` (via a PowerShell `Get-CimInstance`/`Stop-Process` one-liner matched on command line, not by name — never kills an unrelated Python process), backs up the current code (not data) into `_update_backups/` (capped at 5, oldest pruned, same pattern as the DB snapshot cap), installs the new files over this folder, then deletes the temp zip/extraction itself (`tempfile.TemporaryDirectory`) — nothing left for Mario to clean up. Never touches `urto_crm.db`/`backups/`/`outputs/`/`documents/` (a `NEVER_TOUCH` set, on top of those files not shipping in the zip anyway). A small Tkinter status window shows progress and offers a "Launch URTO Now" button when done.
- `Create URTO Updater Desktop Icon.vbs` — one-time setup Mario double-clicks to create the "URTO Updater" Desktop shortcut, mirroring `Create URTO Desktop Icon.vbs`.
- `lookup_engine.py` — Playwright automation of **FOREWARN** (app.forewarn.com). User logs in manually in a headed Chromium window the script opens; automation takes over from there.
- `input_parser.py` — normalizes CSV input into the canonical row format by matching columns **by meaning** (`resolve_headers`/`HEADER_ALIASES`, not exact names) — handles a combined owner-name field (county "LAST FIRST" convention) or separate first/last columns, and either a combined address or house-number/street-name components. Registered-business-entity owners (`REGISTERED_ENTITY_TOKENS`: LLC/Inc/Corp/etc.) are tagged `is_entity` + `entity_name` instead of skipped — see `llc_lookup.py`. Trust names (`TRUST_TOKENS`) get a shot at local person-extraction first (`_try_extract_trust_person` — strips trust words/dates, applies the county convention) before falling back to a skip. Everything else non-individual (churches/banks/placeholders/ambiguous names) still gets an immediate `skip_reason`. Never guesses name order for an ambiguous single "Name" column — only the known county convention.
- `ors_routing.py` — real GPS route optimization for **ShowingDay** (see build order #98), via OpenRouteService's free API (geocoding + VROOM-based `/optimization`, which natively supports pinning a break into a time window — used for the adjustable lunch break). Same "plain `requests`, no heavy SDK" pattern as `google_drive_api.py`/`microsoft_graph_api.py`. Lives in the shared `crm.py`/`crm_routes.py` layer, not `app.py`/`hosted_app.py` directly, so it works on desktop automatically via the existing proxy — unlike Google/Microsoft OAuth (hosted-only), there's no separate desktop-side wiring needed here at all.
- `llc_lookup.py` — resolves an `is_entity` row to a real person via a live **Sunbiz** (Florida Division of Corporations) search in the same shared Chromium page as FOREWARN. `resolve_entity_owner()` returns an ordered `candidates` list rather than a single guess: the registered agent (if it parses as a plain person via the "LAST, FIRST" comma convention), OR — if the agent name is itself a company — the person embedded in a P.A./PLLC/PC-style entity name (`_try_extract_pa_person`, see build order #39) as the first candidate, with every officer/manager that parses as an individual kept as fallback candidates after it. `lookup_engine.process_row()` tries candidates in order, only spending a second real FOREWARN search on a fallback if the first comes back NOT_FOUND. Only trusts the "LAST, FIRST" comma convention Sunbiz uses for individual names, and never guesses word order on an ambiguous multi-person firm name — same caution `input_parser.py` uses. Confirmed working against the live site (see build order #18).
- `forewarn_lookup.py` — CLI entry point (same engine as the web app). Also calls `crm.init_db()` on startup now (needed for the weekly lookup counter table — see below), same as the web app already did.
- `crm.py` — SQLite-backed CRM: clients, notes, recurring follow-ups, **and manual calendar `events`** (separate table, merged into calendar/Dialer views rather than touching the recurring-schedule math). Also owns the **automatic backup system** (see below), the **weekly lookup counter** (`lookup_stats` table, keyed by that week's Monday — `get_weekly_lookup_count()`/`increment_weekly_lookup_count()`), **Transaction Manager** (see build order #22): `document_types` (shared per-type checklist + shared template file), `transactions`, `transaction_documents` (per-transaction snapshotted rows, independent of later checklist edits), and **Contact Lists** (see build order #27): `contact_lists` + `contact_list_members` — a named group of clients sharing one recurring call schedule (`next_call_date`/`interval_days` on the list itself, not per-member). Uploaded files live under `DOCUMENTS_DIR` (`documents/templates/`, `documents/signed/` — both gitignored) via `_store_upload`/`_delete_stored_file`. DB file `urto_crm.db` is gitignored — **never commit real client data**.
- `templates/index.html` — the entire frontend. One file, eight tabs: **Home**, **Owner Lookup** ("URTO Skip Trace" in-app), **URTO CRM**, **URTO Dialer**, **Transactions**, **ShowingDay**, **EOS & Rocks**, **Commissions**. All vanilla JS, no framework. Shared space-themed CSS (`.space-bg`, glass cards, gold glow) applies to every page. Nav is a horizontal top bar on mobile and a `position: sticky` left sidebar on desktop (`.app-body` wraps `.tabs` + `<main>`, see build order #99) — anything that inserts a DOM node above the main content area must anchor on `.app-body`, not `main` directly (see gotcha below).
- `static/urto-space.js` — Three.js WebGL scene for the Home tab, including the 3D skywriting rocket + particle smoke.
- `static/stars.svg` — small static starfield SVG used as the tiled background layer on non-Home pages.
- `static/vendor/three/` — **vendored Three.js + addons**, pulled from the npm tarball (`registry.npmjs.org`), not a CDN. `cdn.jsdelivr.net` and similar CDNs are **blocked by this environment's network policy**.

## Backup system (crm.py)

- **Multiple simultaneous destinations**: `resolve_backup_dirs()` returns EVERY place a backup gets written, not one-or-the-other — always the local `backups/` folder (gitignored, guaranteed baseline) PLUS OneDrive (auto-detected via the `OneDrive`/`OneDriveConsumer` env vars) PLUS Google Drive (see below) whenever each is present. `_write_backup()` loops over all of them; one destination failing (a cloud folder briefly locked) never blocks the others.
- **Google Drive**: detected via **Google Drive for Desktop's Mirror-mode local folder** (`_detect_google_drive_dir()` checks common default paths), NOT the real Google Drive API — deliberately chosen with Mario so this needs zero new account/OAuth setup on his end, same "just write into a locally-synced folder" trick OneDrive already uses. If auto-detect guesses wrong, Mario can paste the real path into a small form in the CRM tab's backup bar (`POST /api/backup/google_drive_dir`), stored in `app_settings` and preferred over auto-detection from then on.
- **Instant mirror**: every CRM mutation calls `on_data_changed()`, which immediately rewrites `urto_crm_latest.db`, the human-readable **CRM Contacts** export, and the **full JSON data export** (see below) to every destination — so deletions propagate right away, not just additions. All three are cheap (small file overwrites), so they run on every single edit, not just periodically.
- **Periodic snapshots**: `backup_now()` also writes a timestamped `urto_crm_YYYYMMDD_HHMMSS.db` snapshot (capped at 30, oldest pruned) to every destination — run on app startup, on the "Backup Now" button (`/api/backup/run`), and by a 60s background watcher.
- **CRM Contacts export** (`_write_crm_contacts_export`): one `.txt` file per client under `CRM Contacts/` in every backup destination — name/phone/address/follow-up status/full notes log, human-readable straight from OneDrive or Google Drive without opening URTO. Full diff each run (stale files for deleted clients are removed).
- **Full JSON data export** (`_write_full_data_export`): a single `URTO_Full_Data_Export.json` per destination containing EVERY table (clients, notes, contact lists + membership, calendar events, transactions + their documents, document checklists, lookup stats) — regenerated on every single instant mirror. Meant to be copy-pasted into a fresh Claude conversation as a complete description of every piece of data currently in URTO. Don't gate this behind the snapshot path — Mario explicitly wants it to change on every add/edit/delete, and it's cheap (a handful of SELECTs + `json.dumps`).
- **Transaction Manager's uploaded documents AND Commission Tracker's per-entry file uploads** are mirrored into human-organized folders per destination (`_mirror_documents_folder`, real original filenames, not the internal stored/uuid ones): `Transaction Checklist Documents/<Type>/<Document Name>.<ext>` (the shared per-type templates), `Transactions/<Title> (id)/<Document Name> - Template/Signed.<ext>` (one folder per actual transaction, across active/closings/archive), and `Commission Files/<Title> (id).<ext>` (one file per commission entry with an attachment, see build order #101). This stays on the periodic/snapshot path for ROUTINE mutations (real files are heavier than a DB overwrite) — **except** the specific document-mutating functions (`set_document_type_template`, `remove_document_type_template`, `delete_document_type`, `upload_signed_document`, `remove_signed_document`, `create_transaction`, `delete_transaction`, `create_commission_entry`/`set_commission_entry_file`/`remove_commission_entry_file`/`delete_commission_entry` when a file's actually involved) which each also call `_instant_document_mirror()` right after `on_data_changed()`, so an uploaded/removed document shows up in the cloud immediately rather than waiting up to 60s — without making every OTHER routine note/follow-up edit pay for real file I/O. Every mirror here is a full diff: copies new/changed files **and deletes ones no longer expected** (removed document, renamed/deleted transaction), so removals actually disappear from every backup destination too. **On the hosted deployment, `_instant_document_mirror()` also fires `crm._push_documents_to_google_drive()` on a background thread** (see build order #101) — the real Google Drive API push for these same files, not just the local/OneDrive-style filesystem mirror; `_iter_document_backup_files()` is the single generator both the local mirror and the Drive push walk, so they can never silently disagree about what should exist. `_prune_drive_folder()` does the equivalent of the local mirror's full `rglob()` cleanup on Drive — a recursive walk of the three known root folders that removes anything no longer expected, including a subfolder that's now completely empty (e.g. a transaction's only signed doc, or a commission entry's only photo, being removed).
- Status surfaced via `/api/backup/status` (per-destination list, not a single bool) and a status bar in the CRM tab showing OneDrive/Google Drive/Local chips plus the Google Drive path-entry form when not auto-detected.
- **`CODE_DOWNLOAD_LINK.txt`** (`_write_code_download_link`): a plain-text pointer to the app's own GitHub ZIP/repo URL, written into every backup destination alongside the data (see build order #41) — so losing the PC entirely is a two-step recovery (GitHub for the code, any one backup folder for the data + this pointer), not something that depends on remembering a URL from somewhere else. Keep its `GITHUB_ZIP_URL` constant in sync with `urto_updater.pyw`'s `REPO_ZIP_URL` if the branch ever changes.

## Hard-won gotchas (don't re-discover these)

- **`templates/index.html`'s entire JS is ONE giant inline `<script>` tag** (see build order #69) — an uncaught synchronous error ANYWHERE in it kills every line after it in that same tag, not just the feature that threw. This bit hosted mode hard: Owner Lookup's setup code runs first and unconditionally dereferenced `resultsTable` (`null` in hosted mode, since that markup is correctly gated out), which silently broke tab-switching/Add Client/Dialer/Transactions — everything after that one line — while the CRM tab kept looking fine only because it's the hardcoded default. Any future `{% if hosted %}`/`{% if not hosted %}` split of this file's markup MUST have a matching split on the JS side too, wrapping the code that references the removed elements — don't assume "the HTML is gone so nobody will call this" protects you; the code still runs unconditionally unless the JS itself is also gated. If a hosted-mode feature is ever reported as "the button does nothing" for something that looks unrelated to what was just changed, check the browser console for an unrelated error earlier in page load before debugging the reported feature itself.
- **A Jinja `{%...%}` tag is recognized anywhere in the raw file, including inside a JS `//` comment** — Jinja has no concept of JS syntax, it just scans raw text for `{%`/`%}` delimiters. Writing an explanatory code comment that mentions Jinja syntax by literally typing e.g. `{% if not hosted %}` inside a `//` comment opens a REAL (unintended) template block and breaks compilation with a confusing "Unexpected end of template" error nowhere near the actual problem (hit and fixed live during build order #69). If a comment needs to reference a Jinja tag by name, describe it in prose instead of pasting the literal delimiter sequence.
- **FOREWARN's form fields use Material-UI floating `<label>`s, not native `placeholder` attributes.** Use `page.get_by_label(...)`, never `get_by_placeholder(...)`.
- **The SEARCH button contains a nested `<span>`**, so `get_by_text()` hits a strict-mode "2 elements" error. Use `get_by_role("button", name=<case-insensitive regex>)`.
- **Never trust the results-list card's address for a match.** Always open each candidate's actual **Address History** page and check it before taking a phone number — a prior shortcut here caused a real wrong-person bug.
- **CDNs are blocked**; use `registry.npmjs.org` tarballs for any new frontend dependency.
- **CSV parsing must match columns by meaning, not exact name.** Real-world exports vary ("Zip Code" vs "Postal Code" vs "Zip"). Never blind-guess name order for a single ambiguous "Name" column — only the known Miami-Dade county "LAST FIRST" convention on a recognized combined owner-name column. Guessing wrong here is exactly the wrong-person bug class above.
- **Not every data source uses the county's "LAST FIRST" convention — some (e.g. IMAPP) ship a combined owner-name column in plain "FIRST LAST" order instead.** `input_parser._detect_name_order()` decides which convention applies ONCE per file, from a signature of columns unique to that kind of export (never per-row, never by guessing at a single ambiguous name) — see build order #34 for how this was actually confirmed (cross-referencing owner names against that same file's recorded-mortgage-borrower field). If a new aggregator export shows up with yet another name-order convention, add a new signature + `name_order` value rather than trying to auto-detect word order from the name itself. **Trust-owned rows are always parsed as "last_first" regardless of the file's detected name_order** — trust ownership names look to carry over from the raw county record even in an otherwise-first-last file (confirmed the same way). Don't change that exemption without similarly strong cross-referenced evidence.
- **A generic "Address"/"City"/"State" column can silently BE a mailing address, not the property's own.** County tax-roll exports for an LLC/entity-owned parcel often carry both — a mailing address (where the owner/registered agent's tax bill goes) and a separate situs/site/property address for the actual parcel. `HEADER_ALIASES` in `input_parser.py` lists situs/site/property aliases FIRST (ahead of the generic ones) for exactly this reason, and `resolve_headers()` hard-excludes any column whose name contains "mailing" outright. Don't reorder those aliases back or relax the mailing exclusion without re-reading build order #30 — that's the exact shape of bug that already shipped once (right person, right phone, wrong property).
- **3D rocket meshes need `depthTest: false`** on their materials (with staggered `renderOrder`) — otherwise they get incorrectly occluded by the logo/orbs/rings that share the same depth range, since the rest of the Home scene uses real opaque 3D geometry.
- **`crm.py`'s backup globals need `global _dirty, _last_backup`** in `backup_now()` — a missed `global` on a reassigned module-level dict silently shadows it with a local, so the function *works* (returns the right value) but the module-level state never updates. Bit us once; if a status endpoint ever looks "stuck," suspect this pattern first.
- **Manual calendar events are a separate `events` table**, deliberately not folded into the recurring-followup math — keeps ad-hoc events from disturbing a client's automatic schedule anchor. `get_calendar_events()` merges both into one list tagged by `kind` ("auto"/"manual").
- **`get_calendar_events()`'s manual-event branch builds its own plain dict by hand instead of just spreading what `EVENT_JOIN_SELECT`/`_event_to_dict()` already fetched** (see build order #89) — a real bug already happened here once: `address` (and later `meeting_type`/`meeting_provider`/`meeting_link`) existed on the underlying row the whole time but were silently missing from this hand-built dict, so an event opened by clicking its CALENDAR CHIP (the common path) showed none of that data, even though "+ Add Event" → edit the same event directly showed it fine (that path reads the row without going through this function). If a new column is ever added to `events`, it must be added to BOTH `EVENT_JOIN_SELECT`'s consumers AND this manual-event dict in `get_calendar_events()` — they are two separate places that both need to agree on the event's shape, not one.
- **A CSS Grid item's default `min-width: auto` means its minimum size is its unwrapped CONTENT width, not its fair share of the track** (see build order #81) — `.cal-cell` (a `repeat(7, 1fr)` grid item) had no explicit `min-width`, so one long unwrapped chip label was enough to force that whole column wider than 1/7 of the grid, blowing the grid's total rendered width past its container's. This is silently invisible on a wide desktop viewport (there's slack to absorb it) but on mobile it hid 4 of the 7 day-of-week columns entirely behind the calendar card's `overflow: hidden`, with zero visible error — it just looked like the calendar was broken. `overflow: hidden`/`text-overflow: ellipsis` on a grid/flex child does NOT work until the child can actually shrink below its content size, which requires an explicit `min-width: 0` (or `min-height: 0` for a column direction) on that child. If a future grid/flex layout in this file ever looks like it's silently clipping or hiding content at narrow widths, check for a missing `min-width: 0`/`min-height: 0` on the item holding unwrapped text before assuming it's something else — `getBoundingClientRect().width` vs `.scrollWidth` on the grid container (a big mismatch is the smoking gun) is the fastest way to confirm it.
- **The Dialer's Enter/arrow keyboard shortcuts must not fire while a modal is open** ("Add to CRM" sits on top of the Dialer) — guarded via `document.querySelector('.modal-overlay.show')` in the keydown handler.
- WebGL testing in this sandbox: `p.chromium.launch(executable_path="/opt/pw-browsers/chromium", args=["--enable-unsafe-swiftshader","--use-gl=angle","--use-angle=swiftshader"])`. A hovered orb intentionally slows its own orbit (`orb.hoverT`) so it's easier to click. **The scene's game-clock (`elapsed`) is heavily throttled in a headless/backgrounded browser** (rAF fires far slower than wall-clock) — for anything timing-gated (like the rocket), temporarily force the trigger via a debug hook (e.g. `window.__flybyDebug().nextAt = 0`) rather than waiting real seconds, and strip the hook before committing.
- **`search.sunbiz.org` is blocked by this sandbox's network policy** (`ERR_TUNNEL_CONNECTION_FAILED`) — same restriction that already applies to FOREWARN, documented in README's "Known fragile spots". `llc_lookup.py`'s selectors/text-labels were written from Sunbiz's known, long-stable page structure, verified in this sandbox only against **local HTML fixtures** standing in for the real site — but confirmed working against the actual live site on Mario's first real run (see build order #18). If a future row still fails to resolve unexpectedly, use `--debug` (threads through from the CLI's existing `--debug` flag into `resolve_entity_owner`) to pause with Playwright Inspector at the search box and again after the results/detail page loads.
- **Sunbiz officer/registered-agent names only parse when the "LAST, FIRST" comma convention is present** (`_split_person_name` in `llc_lookup.py`) — deliberately refuses to guess word order otherwise, matching `input_parser.py`'s existing name-order caution. - **Every dialer source funnels through `loadDialerList()`** (see build order #59) — this is deliberate and should stay that way: it's the one place that runs `dedupeDialerEntries()` (collapsing repeat phone numbers, e.g. one owner with multiple properties on a lookup-results CSV) and `matchEntriesToClients()` (CRM phone cross-reference). If a future dialer source is added, route it through `loadDialerList()` rather than rendering the dial list directly — bypassing it silently reintroduces both the duplicate-call bug and the missing "In your CRM" matching. **Missed Follow-ups** (build order #65) is the newest example of this pattern — its click handler does nothing but fetch `/api/crm/followups/missed` and hand the results to `loadDialerList()`, same as every other source.
- **`on_data_changed()`'s instant mirror runs on a background thread, not inline in the request** (see build order #83) — it used to call `backup_instant()` synchronously, which on the hosted deployment includes a real Google Drive API round-trip (OAuth token refresh + uploads); a slow connection there could stretch an ordinary save long enough to hit Render's own request timeout, surfacing to Mario as "Saving... forever" then "Couldn't reach URTO's server." Don't write code that assumes the mirror/Google-Drive-push has already completed by the time `on_data_changed()` (or any function that calls it, e.g. `create_client`/`create_event`) returns — it's fire-and-forget from that point on, backed by `_write_backup()`'s own `_backup_lock` for safety, not a synchronous guarantee. If a future feature genuinely needs to know a backup finished, it needs its own explicit wait/callback, not "call `on_data_changed()` then assume it's done."
- **`_send_push_to_all()`'s `webpush()` call is a real synchronous outbound HTTPS request with no timeout by default, and pywebpush does NOT wrap its own `requests.post()` call in any try/except** (see build order #85) — the exact same "slow external network call blocks a user-facing request" bug as `on_data_changed()` above, hit for real when Mario's own "Send Test" button tap timed out. `webpush()` is now always called with `timeout=15`, and `_send_push_to_all()` catches `requests.exceptions.RequestException` alongside `WebPushException` in its per-subscription loop (a bare timeout is NOT a `WebPushException`, so the old code would have let it propagate uncaught and abort delivery to every other subscription still left in the loop) -- but a timeout must never call `crm.remove_push_subscription()`, only a real `WebPushException` carrying a 404/410 response should ever do that. **Any future route that calls `_send_push_to_all()` directly in its own request handler** (not from one of the existing background watcher threads, which already tolerate this fine) **must fire it on a background thread**, exactly like `push_test()` does — never call it inline and make the user's tap wait on real push-delivery network I/O.
- **`VAPID_PRIVATE_KEY_PEM`/`VAPID_PUBLIC_KEY_B64` must be the RAW base64url-encoded value with NO `-----BEGIN/END-----` PEM wrapper and no internal newlines** (see build order #87) — `py_vapid`'s `Vapid.from_string()` only strips `\n` characters before base64url-decoding; it does not strip PEM header/footer text, so a full PEM block pasted into either env var decodes to garbage and `webpush()` raises a bare `ValueError` (`"Could not deserialize key data... ASN.1 parsing error"`) on every single push attempt — this is exactly what silently broke every push notification Mario ever tried to send, discovered only once `_send_push_to_all()`'s `[push]`-prefixed logging (build order #86) made the crash visible in Render's Logs tab. If VAPID keys are ever regenerated for this project again, generate them the same way build order #87 did (`py_vapid`'s `Vapid02().generate_keys()`, then export the private key as DER + base64url via `private_bytes(Encoding.DER, PrivateFormat.PKCS8, NoEncryption())` and the public key as an uncompressed point + base64url via `public_bytes(Encoding.X962, PublicFormat.UncompressedPoint)`) and sanity-check the result with `Vapid.from_string()` before handing it to Mario — don't just paste a PEM file's contents into the env var.
- **`os.environ.get(key, default)`'s default only kicks in when the key is completely ABSENT, not when it's present-but-blank** (see build order #88) — Render's Blueprint setup wizard creates every `sync: false` env var as soon as Mario submits the form, even if he leaves one field empty, so a skipped/blank field is genuinely a different state than "never set" and silently defeats a `.get(key, "sane default")` fallback. This bit `VAPID_CLAIM_EMAIL` for real (an empty string reached `py_vapid` and failed its `sub` claim validation on every single push). Any future required-but-optional env var in this file should normalize explicitly (`(os.environ.get(key) or "").strip()`, falling back to the default when that's empty) rather than trusting `.get(key, default)` alone to catch a blank value.
- **A new SQLite table never needs any new backup plumbing** — `_write_backup()`'s instant mirror is a whole-file `shutil.copy2()` of the live DB, not a table-by-table export, so any table added to `init_db()` (e.g. `call_log`, build order #58) is captured automatically the moment a row is written. Only the human-readable exports (`_write_full_data_export()`'s JSON, `_write_crm_contacts_export()`) need an explicit new line added if a new table should appear in THOSE — the raw `.db` mirror/snapshot files never need touching.
- **Any loop that calls `create_client`/`update_client`/`add_note` (or anything else that ends in `on_data_changed()`) more than a handful of times must wrap the loop in `with _deferred_backup():`** (see build order #61) — each of those calls normally triggers a FULL instant backup mirror (whole-DB copy + a re-written CRM Contacts `.txt` per existing client + the full JSON export, to every destination), so a bare loop over N rows does up to N full mirror passes instead of one. This is genuinely slow on a real CRM with existing clients and/or synced OneDrive/Google Drive folders — it's what made the Outlook recurring-follow-up import look permanently hung on Mario's first real run. Both existing bulk-import functions (`import_recurring_followups_csv`, `import_contact_list_file`) and `merge_clients()` (build order #63) already do this; copy the same pattern for any future bulk-write feature (a future "bulk edit clients" tool, a bigger CSV import, etc.) rather than calling the normal single-row functions bare in a loop.
- **A re-run of an import can only prevent NEW duplicates — it can never retroactively merge rows that already exist as separate client records** (see build order #63) — `_find_recurring_import_match()` stops a re-import from creating MORE duplicates going forward, but a client already split into 2+ database rows from an earlier bad run stays split forever unless something actually reassigns/deletes the extra rows. Mario asked for exactly this once ("make it so when I add contacts again it replaces and this is fixed") and re-importing alone genuinely can't deliver it — say so plainly rather than implying a re-import will clean up existing data. `find_duplicate_clients()`/`merge_clients()` is the actual cleanup path: it groups by exact name, reassigns notes/call_log/events/contact_list_members from the losing copies onto the kept one (never deletes real history, just relocates it), and only then deletes the merged-away rows.
- **In this sandbox's headless Chromium, clicking a real `tel:` link with no registered handler leaves the page unable to receive further real clicks** (discovered testing build order #58) — Chromium's native "open in another app?" prompt for an unhandled custom scheme apparently gets stuck open, silently swallowing all subsequent pointer input (confirmed: a capturing `click` listener on `window` stops firing entirely afterward), without ever firing Playwright's `dialog` event (that's for `window.alert/confirm/prompt` only, not this). A JS-triggered `.click()` or a direct function call still works fine — only real Playwright mouse clicks after a real `tel:` navigation attempt are affected. When a test needs to simulate "a call was just placed" and then interact with the page further, call `logCallForEntry(entry)` (or whatever the actual click handler is) directly via `page.evaluate()` instead of clicking the real Call button — this is a test-environment artifact only, not a real app bug, since Mario's actual PC has Phone Link registered as the `tel:` handler.
- **Any timestamp shown to Mario must be 12-hour with AM/PM, never bare 24-hour** (see build order #57) — the footer's "last updated" and `formatLastCalled()` already got this right from the start (`%I:%M %p` / `toLocaleTimeString` with `hour: 'numeric'`, which defaults to 12-hour in the `en-US` locale used everywhere here), but a raw stored value displayed with no reformatting (notes' `"YYYY-MM-DD HH:MM"`, a calendar event's plain `"HH:MM"`) will silently come out 24-hour. Use `formatNoteTime()`/`formatTime12()` for any new spot that displays one of these two raw storage shapes — don't `new Date()`-parse a space-separated (non-`T`) datetime string directly, since that isn't reliably parsed the same way across browsers.
- **Testing `parseVoiceCommand()`/voice-fill in Playwright requires a mocked `SpeechRecognition` that mimics the real "still listening until manually stopped" behavior** — a mock that fires `onresult` + `onend` together on a timer (rather than only firing `onend` when `.stop()` is called) triggers the app's real continuous-listening auto-restart loop (`onend` calls `recognition.start()` again whenever `voiceRecognizing && !voiceManualStop`, mirroring build order #14's dictation), producing a runaway loop that appends the transcript repeatedly and never reaches the "parse it" branch. The working test pattern: `start()` fires `onresult` once and does nothing further; `stop()` is what fires `onend` (after a short delay) — then drive the test with two clicks (start, then stop) exactly like a real user would.
- **`window.speechSynthesis` is a native, non-configurable browser property in Chromium (even headless) — a plain `window.speechSynthesis = {...}` assignment in a Playwright test silently fails and leaves the real native object in place**, so the app ends up calling the REAL `speechSynthesis.speak()` (a no-op with no observable effect in headless mode) instead of the intended mock, and any assertion on "was speak() called with X" just never fires with no error to explain why. Discovered testing build order #75's morning voice briefing. The fix is `Object.defineProperty(window, "speechSynthesis", { value: mockSynth, configurable: true })` instead of a plain assignment — this actually overrides the native property. Same caution likely applies to any other native browser API a future feature needs to mock (don't assume a plain assignment works just because it doesn't error).
- **`crm.py` never stores a client's original follow-up preset key ("2_weeks" etc.) — only the resolved `(frequency_label, interval_days)`** (see build order #112) — so ANY code that repopulates the Add/Edit Client form for editing must reverse-map `interval_days` back onto `cfFrequency`'s `<select>` itself (`applyClientFrequencyToForm()`, matching against the fixed day-counts, or falling back to an exact "custom, N Days" entry — `"days"` is the only unit that round-trips 1:1 through `resolve_interval_days()` with zero rounding). This was a real, already-shipped bug: `cdEditBtn`'s handler never did this, so `resetClientForm()`'s default (`cfFrequency.value = '4_weeks'`) silently won on every single client edit whose real schedule wasn't already 4 weeks — `update_client()`'s "only reset the anchor if the frequency genuinely changed" guard saw a real (if accidental) change every time, and quietly reset `next_followup_date` to today+28. If a future form/flow ever repopulates a client for editing, it must go through `applyClientFrequencyToForm()` (or an equivalent reverse-mapping) rather than assuming a fetched client object carries anything named `frequency_key` — it never does.
- **Two CRM clients can never share one phone number; a manual calendar event's `list_id` and a Contact List's own recurring schedule are two independent things that must never touch each other** (see build order #54). `crm.find_client_by_phone()` compares phone numbers digits-only with the US country code stripped (`_normalize_phone_key`) so formatting differences never let a real duplicate slip through — `create_client`/`update_client` both call it and raise `DuplicatePhoneError` (→ HTTP 409) before writing anything. This is a DIFFERENT rule from "a client can belong to multiple Contact Lists," which is still fully allowed and unrelated — don't conflate the two if this area changes again. Separately, `create_event`/`update_event`'s `list_id` only exists to let a manual one-off reminder reference a whole Contact List instead of one client; it must never write to `contact_lists.interval_days`/`next_call_date` — those only ever change via `complete_list_round()`. If a future feature touches either of these paths, keep re-verifying both invariants directly (create/update an event, diff the list's schedule fields before/after) rather than assuming — this is exactly the class of "quiet cross-contamination" bug this codebase has hit before with the recurring-followup anchor date (see the manual-events-are-a-separate-table gotcha above).
