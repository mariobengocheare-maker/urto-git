# URTO — Ultimate Realtor Tool

Solo-user local tool for a Miami-Dade real estate agent (Mario Bengochea). Flask + vanilla HTML/CSS/JS — **no build step, no npm install, no React/Tailwind/TypeScript**. Runs as `python app.py`, opened at `http://localhost:5000` on the user's own Windows PC.

33. Mario shared a real results CSV (60 rows: 34 FOUND / 14 SKIPPED / 12 NOT_FOUND) asking to analyze the misses. Two were genuine parsing bugs, now fixed: (1) `llc_lookup._split_person_name()` only handled Sunbiz's `"LAST, FIRST"` comma convention — a registered agent with a generational suffix is often listed as a THIRD comma segment, `"LAST, SUFFIX, FIRST"` (e.g. `"HACKETT, II, JOHN"`), which the old first-comma-only split mangled into a garbage name (`"Ii, Hackett"`, `owner` field literally containing a stray comma). Added a specific 3-part-with-known-suffix case (`_NAME_SUFFIXES`) rather than guessing generically. (2) `"PLLC"`/`"PA"`/`"PLC"`/`"PC"`/`"CHARTERED"` (professional-entity suffixes law firms commonly use as their own registered name, e.g. a firm serving as someone's registered agent) weren't in `ENTITY_TOKENS`, so `_looks_like_company()` didn't recognize `"NEIMAN & INTERIAN, PLLC"` as a company and tried to parse it as a person's name (`"Pllc Neiman & Interian"`). Added to both `ENTITY_TOKENS` and `REGISTERED_ENTITY_TOKENS`. Also added `"AGR"`/`"AGMT"`/`"REV"`/`"LIV"`/`"TR"` to `TRUST_STOPWORDS` — `"ZANN ELIZABETH A REV TRUST AGR 4/12/2018"` was skipping outright because trailing-word stripping stopped at the unrecognized `"AGR"`, leaving `"TRUST"` stuck in the middle of the remaining tokens and tripping the entity-token rejection check. The remaining 9 NOT_FOUNDs in that CSV were genuine FOREWARN misses (no candidate's address history matched, or zero FOREWARN results for that name/zip) — not bugs, and not "fixed" by guessing; one (`"TIMOTHY D ONNEN REVOCABLE TRUST"` → `"D Timothy"`) was flagged to Mario as ambiguous-name-order rather than silently changed, since the trust name might be self-authored in plain first-middle-last order instead of the county's usual "LAST FIRST MIDDLE" convention, and guessing wrong here is exactly the wrong-person bug class this file exists to avoid.
34. Mario tried a different data source for the same property (IMAPP's "Detailed Summary" export instead of a raw county tax-roll) and asked if it would help. ## Backup system (crm.py)

- **Multiple simultaneous destinations**: `resolve_backup_dirs()` returns EVERY place a backup gets written, not one-or-the-other — always the local `backups/` folder (gitignored, guaranteed baseline) PLUS OneDrive (auto-detected via the `OneDrive`/`OneDriveConsumer` env vars) PLUS Google Drive (see below) whenever each is present. `_write_backup()` loops over all of them; one destination failing (a cloud folder briefly locked) never blocks the others.
- **Google Drive**: detected via **Google Drive for Desktop's Mirror-mode local folder** (`_detect_google_drive_dir()` checks common default paths), NOT the real Google Drive API — deliberately chosen with Mario so this needs zero new account/OAuth setup on his end, same "just write into a locally-synced folder" trick OneDrive already uses. If auto-detect guesses wrong, Mario can paste the real path into a small form in the CRM tab's backup bar (`POST /api/backup/google_drive_dir`), stored in `app_settings` and preferred over auto-detection from then on.
- **Instant mirror**: every CRM mutation calls `on_data_changed()`, which immediately rewrites `urto_crm_latest.db`, the human-readable **CRM Contacts** export, and the **full JSON data export** (see below) to every destination — so deletions propagate right away, not just additions. All three are cheap (small file overwrites), so they run on every single edit, not just periodically.
- **Periodic snapshots**: `backup_now()` also writes a timestamped `urto_crm_YYYYMMDD_HHMMSS.db` snapshot (capped at 30, oldest pruned) to every destination — run on app startup, on the "Backup Now" button (`/api/backup/run`), and by a 60s background watcher.
- **CRM Contacts export** (`_write_crm_contacts_export`): one `.txt` file per client under `CRM Contacts/` in every backup destination — name/phone/address/follow-up status/full notes log, human-readable straight from OneDrive or Google Drive without opening URTO. Full diff each run (stale files for deleted clients are removed).
- **Full JSON data export** (`_write_full_data_export`): a single `URTO_Full_Data_Export.json` per destination containing EVERY table (clients, notes, contact lists + membership, calendar events, transactions + their documents, document checklists, lookup stats) — regenerated on every single instant mirror. Meant to be copy-pasted into a fresh Claude conversation as a complete description of every piece of data currently in URTO. Don't gate this behind the snapshot path — Mario explicitly wants it to change on every add/edit/delete, and it's cheap (a handful of SELECTs + `json.dumps`).
- **Transaction Manager's uploaded documents** are mirrored into two human-organized folders per destination (`_mirror_documents_folder`, real original filenames, not the internal stored/uuid ones): `Transaction Checklist Documents/<Type>/<Document Name>.<ext>` (the shared per-type templates) and `Transactions/<Title> (id)/<Document Name> - Template/Signed.<ext>` (one folder per actual transaction, across active/closings/archive). This stays on the periodic/snapshot path for ROUTINE mutations (real files are heavier than a DB overwrite) — **except** the specific document-mutating functions (`set_document_type_template`, `remove_document_type_template`, `delete_document_type`, `upload_signed_document`, `remove_signed_document`, `create_transaction`, `delete_transaction`) which each also call `_instant_document_mirror()` right after `on_data_changed()`, so an uploaded/removed document shows up in the cloud immediately rather than waiting up to 60s — without making every OTHER routine note/follow-up edit pay for real file I/O. Every mirror here is a full diff: copies new/changed files **and deletes ones no longer expected** (removed document, renamed/deleted transaction), so removals actually disappear from every backup destination too.
- Status surfaced via `/api/backup/status` (per-destination list, not a single bool) and a status bar in the CRM tab showing OneDrive/Google Drive/Local chips plus the Google Drive path-entry form when not auto-detected.
- **`CODE_DOWNLOAD_LINK.txt`** (`_write_code_download_link`): a plain-text pointer to the app's own GitHub ZIP/repo URL, written into every backup destination alongside the data (see build order #41) — so losing the PC entirely is a two-step recovery (GitHub for the code, any one backup folder for the data + this pointer), not something that depends on remembering a URL from somewhere else. Keep its `GITHUB_ZIP_URL` constant in sync with `urto_updater.pyw`'s `REPO_ZIP_URL` if the branch ever changes.

## Hard-won gotchas (don't re-discover these)

- **`templates/index.html`'s entire JS is ONE giant inline `<script>` tag** (see build order #69) — an uncaught synchronous error ANYWHERE in it kills every line after it in that same tag, not just the feature that threw. This bit hosted mode hard: Owner Lookup's setup code runs first and unconditionally dereferenced `resultsTable` (`null` in hosted mode, since that markup is correctly gated out), which silently broke tab-switching/Add Client/Dialer/Transactions — everything after that one line — while the CRM tab kept looking fine only because it's the hardcoded default. Any future `{% if hosted %}`/`{% if not hosted %}` split of this file's markup MUST have a matching split on the JS side too, wrapping the code that references the removed elements — don't assume "the HTML is gone so nobody will call this" protects you; the code still runs unconditionally unless the JS itself is also gated. If a hosted-mode feature is ever reported as "the button does nothing" for something that looks unrelated to what was just changed, check the browser console for an unrelated error earlier in page load before debugging the reported feature itself.
- **A Jinja `{%...%}` tag is recognized anywhere in the raw file, including inside a JS `//` comment** — Jinja has no concept of JS syntax, it just scans raw text for `{%`/`%}` delimiters. Writing an explanatory code comment that mentions Jinja syntax by literally typing e.g. `{% if not hosted %}` inside a `//` comment opens a REAL (unintended) template block and breaks compilation with a confusing "Unexpected end of template" error nowhere near the actual problem (hit and fixed live during build order #69). If a comment needs to reference a Jinja tag by name, describe it in prose instead of pasting the literal delimiter sequence.
- **FOREWARN's form fields use Material-UI floating `<label>`s, not native `placeholder` attributes.** Use `page.get_by_label(...)`, never `get_by_placeholder(...)`.
- **The SEARCH button contains a nested `<span>`**, so `get_by_text()` hits a strict-mode "2 elements" error. Use `get_by_role("button", name=<case-insensitive regex>)`.
- **Never trust the results-list card's address for a match.** Always open each candidate's actual **Address History** page and check it before taking a phone number — a prior shortcut here caused a real wrong-person bug.
- **CDNs are blocked**; use `registry.npmjs.org` tarballs for any new frontend dependency.
- **CSV parsing must match columns by meaning, not exact name.** Real-world exports vary ("Zip Code" vs "Postal Code" vs "Zip"). Never blind-guess name order for a single ambiguous "Name" column — only the known Miami-Dade county "LAST FIRST" convention on a recognized combined owner-name column. Guessing wrong here is exactly the wrong-person bug class above.
- **Not every data source uses the county's "LAST FIRST" convention — some (e.g. IMAPP) ship a combined owner-name column in plain "FIRST LAST" order instead.** `input_parser._detect_name_order()` decides which convention applies ONCE per file, from a signature of columns unique to that kind of export (never per-row, never by guessing at a single ambiguous name) — see build order #34 for how this was actually confirmed (cross-referencing owner names against that same file's recorded-mortgage-borrower field). If a new aggregator export shows up with yet another name-order convention, add a new signature + `name_order` value rather than trying to auto-detect word order from the name itself. **Trust-owned rows are always parsed as "last_first" regardless of the file's detected name_order** — trust ownership names look to carry over from the raw county record even in an otherwise-first-last file (confirmed the same way). Don't change that exemption without similarly strong cross-referenced evidence.
- **A generic "Address"/"City"/"State" column can silently BE a mailing address, not the property's own.** County tax-roll exports for an LLC/entity-owned parcel often carry both — a mailing address (where the owner/registered agent's tax bill goes) and a separate situs/site/property address for the actual parcel. `HEADER_ALIASES` in `input_parser.py` lists situs/site/property aliases FIRST (ahead of the generic ones) for exactly this reason, and `resolve_headers()` hard-excludes any column whose name contains "mailing" outright. Don't reorder those aliases back or relax the mailing exclusion without re-reading build order #30 — that's the exact shape of bug that already shipped once (right person, right phone, wrong property).
- **3D rocket meshes need `depthTest: false`** on their materials (with staggered `renderOrder`) — otherwise they get incorrectly occluded by the logo/orbs/rings that share the same depth range, since the rest of the Home scene uses real opaque 3D geometry.
- **`crm.py`'s backup globals need `global _dirty, _last_backup`** in `backup_now()` — a missed `global` on a reassigned module-level dict silently shadows it with a local, so the function *works* (returns the right value) but the module-level state never updates. Bit us once; if a status endpoint ever looks "stuck," suspect this pattern first.
- **Manual calendar events are a separate `events` table**, deliberately not folded into the recurring-followup math — keeps ad-hoc events from disturbing a client's automatic schedule anchor. `get_calendar_events()` merges both into one list tagged by `kind` ("auto"/"manual").
- **The Dialer's Enter/arrow keyboard shortcuts must not fire while a modal is open** ("Add to CRM" sits on top of the Dialer) — guarded via `document.querySelector('.modal-overlay.show')` in the keydown handler.
- WebGL testing in this sandbox: `p.chromium.launch(executable_path="/opt/pw-browsers/chromium", args=["--enable-unsafe-swiftshader","--use-gl=angle","--use-angle=swiftshader"])`. A hovered orb intentionally slows its own orbit (`orb.hoverT`) so it's easier to click. **The scene's game-clock (`elapsed`) is heavily throttled in a headless/backgrounded browser** (rAF fires far slower than wall-clock) — for anything timing-gated (like the rocket), temporarily force the trigger via a debug hook (e.g. `window.__flybyDebug().nextAt = 0`) rather than waiting real seconds, and strip the hook before committing.
- **`search.sunbiz.org` is blocked by this sandbox's network policy** (`ERR_TUNNEL_CONNECTION_FAILED`) — same restriction that already applies to FOREWARN, documented in README's "Known fragile spots". `llc_lookup.py`'s selectors/text-labels were written from Sunbiz's known, long-stable page structure, verified in this sandbox only against **local HTML fixtures** standing in for the real site — but confirmed working against the actual live site on Mario's first real run (see build order #18). If a future row still fails to resolve unexpectedly, use `--debug` (threads through from the CLI's existing `--debug` flag into `resolve_entity_owner`) to pause with Playwright Inspector at the search box and again after the results/detail page loads.
- **Sunbiz officer/registered-agent names only parse when the "LAST, FIRST" comma convention is present** (`_split_person_name` in `llc_lookup.py`) — deliberately refuses to guess word order otherwise, matching `input_parser.py`'s existing name-order caution. It also handles the 3-segment `"LAST, SUFFIX, FIRST"` shape (e.g. `"HACKETT, II, JOHN"`) as its own explicit case via `_NAME_SUFFIXES` — do NOT try to generalize that into "just take the last comma segment as first name," since a name with a real middle name after a 2-segment split (`"LAST, FIRST MIDDLE"`) would then break. If Mario reports a real LLC row skipping with "couldn't confidently resolve" and the Sunbiz page clearly shows a resolvable person, the name format on the live page is probably not one of these two recognized shapes — check with `--debug` before loosening anything.
- **A registered-agent-service company (CT Corporation System, Registered Agents Inc, etc.) must not be mistaken for a person** — `_looks_like_company()` checks both `ENTITY_TOKENS` and a small `AGENT_SERVICE_KEYWORDS` list before falling back to the officers/managers list. `ENTITY_TOKENS` includes professional-entity suffixes (`PLLC`/`PA`/`PLC`/`PC`) since law/professional firms commonly serve as someone's registered agent and would otherwise get misparsed as a person's name (e.g. `"NEIMAN & INTERIAN, PLLC"` → garbage `"Pllc Neiman & Interian"`). If a new agent-service firm or entity suffix shows up as a false "person" match, add its name fragment to `AGENT_SERVICE_KEYWORDS`/`ENTITY_TOKENS` rather than loosening the entity-token check itself. **`_looks_like_company()`'s tokenizer strips periods with no replacement (not a space)** before splitting — a dotted abbreviation like `"P.A."` or `"L.L.C."` must collapse to `"PA"`/`"LLC"` to match `ENTITY_TOKENS`; replacing periods with spaces instead (the old, buggy behavior) splits it into single letters that never match anything. If a new dotted suffix shows up unrecognized, check this collapsing step before assuming the token itself is missing from `ENTITY_TOKENS`.
- **A P.A./PLLC/PC-style registered agent is itself named after the actual licensed professional** (Florida requires this) — `_try_extract_pa_person()` strips a trailing `PA_STYLE_SUFFIXES` token and reads the rest as that person's own plain "First Last" name, and `resolve_entity_owner()` puts it FIRST in the returned `candidates` list (searched on FOREWARN before the slower officer/manager fallback, not instead of it — see build order #39, an explicit Mario design call: "keep BOTH options... higher success rate"). Refuses to extract when `"&"` is among the remaining tokens (a multi-partner firm name like `"NEIMAN & INTERIAN, PLLC"` doesn't belong to one single person) — don't remove that guard, it's the same word-order-ambiguity caution used everywhere else in this file.
- **Trust-name person extraction (`_try_extract_trust_person`) only strips a fixed `TRUST_STOPWORDS` set and a trailing date token** — a trust suffix phrasing not in that set will just fail to strip and fall through to the surname-only skip, not silently guess wrong (this already bit one real row — `"...REV TRUST AGR <date>"` stopped stripping at the then-unrecognized `"AGR"`, leaving `"TRUST"` stuck mid-list and tripping the entity-token rejection; fixed by adding `AGR`/`AGMT`/`REV`/`LIV`/`TR` to `TRUST_STOPWORDS`). If a real trust row should've resolved but didn't, check what trailing words are actually in the raw name and add them to `TRUST_STOPWORDS` rather than loosening the "must have 2+ tokens left" rule. Conversely, when a trust's name genuinely isn't in the county's "LAST FIRST MIDDLE" convention (some are self-authored in plain first-middle-last order), don't guess — flag it instead, the same as any other ambiguous name order in this file.
- **The weekly lookup counter increments once per actual FOREWARN search** (inside `lookup_engine._run_forewarn_search`, not per input CSV row) — a row `SKIPPED` at input-parsing time, or an `is_entity` row whose Sunbiz resolution fails, returns before ever reaching that function and correctly doesn't count. If the count ever looks off, check whether something new is short-circuiting before `_run_forewarn_search` (should not count) or after it (should count). A fallback candidate retry (see the P.A./PLLC gotcha above) is a genuinely separate FOREWARN search, so it correctly counts again.
- **`app.py` (desktop) NEVER imports or registers `crm_bp` from `crm_routes.py` again** (see build order #71) — desktop's CRM/Dialer/Transactions/Calendar routes are all forwarded to the hosted server through `hosted_sync.py`'s generic proxy instead. Re-adding `crm_bp` locally would silently create a SECOND, separate local database that could drift from the real one on Render — exactly the two-copies-out-of-sync problem "one cloud" was built specifically to avoid. If a desktop-only feature is ever needed again, it belongs in `app.py` directly (like Skip Trace already is), not behind a locally-registered CRM blueprint.
- **Any new CRM-side route must land under one of `crm_routes.py`'s existing four prefixes** (`/api/crm`, `/api/backup`, `/api/txn`, `/api/text_presets`) to automatically work on desktop — `hosted_sync.py`'s proxy forwards those prefixes generically, with no per-route list to keep in sync. A route added under a genuinely new prefix needs that prefix added to `hosted_sync.PROXY_PREFIXES` too, or desktop will 404 on it while the phone works fine (silently confusing, since it'd look "half broken").
- **The hosted deployment's login is a Flask session cookie, NOT HTTP Basic Auth** (see build order #70) — Basic Auth was tried first and had to be ripped out because an installed iOS PWA (Add to Home Screen) runs in an isolated WebKit context that doesn't reliably keep Basic Auth credentials captured in a normal Safari tab, so Mario kept getting bounced back to a blank "Authentication required" page reopening the Home Screen icon. A real login page + ordinary cookie doesn't have this problem — cookies persist in standalone PWA mode exactly like any other website. If `hosted_app.py`'s auth ever needs revisiting, don't reach for Basic Auth again for this reason. Any new route that should be reachable WITHOUT being logged in (a future health-check endpoint, say) must be added to `_PUBLIC_ENDPOINTS` by its Flask endpoint name (defaults to the view function's name) — forgetting this makes `_require_auth()` redirect it to `/login`, which is usually what you want (fail toward requiring login) but will break something meant to be public, like `/manifest.json`/`/sw.js`/`/static/*` already are.
- **`urto_crm.db` and `documents/` live in `%LOCALAPPDATA%\URTO`, NOT inside the project folder** (`crm.py`'s `DATA_DIR`/`_resolve_data_dir()`) — this was a real bug once (Mario's weekly lookup counter reset, see build order #38): every project-folder-relative path is at risk of vanishing the moment an update lands in a freshly-extracted folder instead of the one currently in use. `_migrate_legacy_data_dir()` runs once on import and copies forward an old in-project-folder DB/documents folder the first time this fix's code runs, so existing data isn't lost — but never move `DATA_DIR` back to being project-folder-relative, and if a future feature adds any new persisted file, put it under `DATA_DIR`, not next to `crm.py`. **`DATA_DIR` is unconditionally `mkdir()`'d right after being computed** (see build order #68) — `sqlite3.connect()` doesn't create missing parent directories on its own, and this was a real crash on Mario's first Render deploy (a brand-new persistent disk has nothing on it yet, so nothing had ever created the folder). Desktop never hit this only because `%LOCALAPPDATA%\URTO` already existed from prior use — don't remove this `mkdir()` call thinking it's redundant.
- **Backups write to a LIST of destinations (`resolve_backup_dirs()`), never just one** (see build order #40) — always Local, plus OneDrive and/or Google Drive whenever detected/configured, all three able to be present simultaneously. If you add any new kind of backup export, loop over `resolve_backup_dirs()` like `_write_backup()` already does — don't special-case "the" backup dir singular, that assumption is gone. Google Drive detection is a **local folder path guess** (Google Drive for Desktop's Mirror mode), not the real Google Drive API — there's no env var Google sets the way OneDrive does, so a wrong guess is expected sometimes; that's why the manual override (`set_google_drive_dir`, stored in `app_settings`) exists and always wins over auto-detection.
- **The full JSON data export (`URTO_Full_Data_Export.json`) and the CRM Contacts `.txt` files are deliberately on the INSTANT mirror path, not gated behind the snapshot cadence** — they're cheap (small text, a handful of SELECTs), and Mario explicitly wants them to reflect every single add/edit/delete, not just whatever the periodic snapshot last caught. Don't move them to the snapshot-only path to "optimize" — that would silently reintroduce the staleness he specifically asked to avoid.
- **Transaction Manager's document checklist is only ever seeded once**, gated by an `app_settings` row (`document_types_seeded`), not by "is the table empty" — Mario deliberately deleting every document off a type down to zero must never cause them to silently reappear on the next restart. If you ever add more seed data, extend `DEFAULT_DOCUMENT_TYPES` and don't touch the seeding gate.
- **A transaction's documents are a snapshot, not a live join** — `transaction_documents.name` is copied at creation time and `document_type_id` is `ON DELETE SET NULL` (not `CASCADE`). Deleting or renaming a document from a type's checklist later must never change or orphan an already-created transaction's row or its uploaded signed file. Only the shared **template** (via the still-linked `document_type_id`) can disappear from an existing transaction's view if the type-level template is later removed — the transaction's own signed upload is never affected either way.
- **Document-folder backup mirroring intentionally only runs on the snapshot path** (`_write_backup(..., snapshot=True)`), not on every `on_data_changed()` instant-mirror call — see "Backup system" above. If a new document-related mutation needs to show up in backups faster than ~60s, don't naively add a full folder copy to the instant path; that's real file I/O on every single edit, unlike the tiny SQLite overwrite the instant path was designed around.
- **`urto_updater.pyw` kills the old server by matching the process's command line** (`Get-CimInstance Win32_Process | Where-Object CommandLine -like '*app.py*'`), never by process **name** (`pythonw.exe`/`python.exe`) — Mario could have other unrelated Python programs running, and killing by name would take those down too. If a future change ever needs to find/stop the running URTO process elsewhere, reuse this same command-line-match approach, not a name-based one.
- **Never hand-type `APP_VERSION_DATE`/a "last updated" timestamp again** (see build order #43) — it always drifts from Mario's real local time since I can't know his actual clock at ship time. The footer's date comes from `app.py`'s `_get_last_updated_display()`, which reads `last_updated.txt` (written by `urto_updater.pyw` using the installing PC's own clock) — if a future feature needs a "when did this last happen" timestamp anywhere in the UI, follow this same pattern (read it from the machine it's actually running on) rather than typing a guess into source.
- **`crm.py` NEVER calls bare `datetime.now()`/`date.today()` — always `_now()`/`_today()`** (see build order #70) — these wrap `datetime.now(ZoneInfo("America/New_York"))` and strip the tzinfo back off, so every stored timestamp is genuine Miami wall-clock time (byte-identical string shape to before, so no frontend parsing changed) regardless of what timezone the machine actually running the code is set to. This mattered a lot once the hosted deployment (Render, UTC clock) went live: a bare `date.today()` there landed on the WRONG calendar day for a chunk of every evening (whenever UTC has already crossed midnight but Miami hasn't), silently shifting follow-up due dates, not just displaying a wrong clock time. If a future function needs "right now" or "today" for anything that gets stored or shown to Mario, use these helpers — never add a new bare `datetime.now()`/`date.today()` call to this file.
- **The footer timestamp is always re-zoned to `ZoneInfo("America/New_York")` before display** (see build order #46), regardless of what timezone the installing PC's system clock is actually set to — a fixed-UTC-offset `tzinfo` (what `datetime.now().astimezone()` produces) has no real name for `%Z` to print, only a numeric offset, hence the old "UTC-04:00" bug. `tzdata` is in `requirements.txt` specifically so this resolves reliably on Windows, which has no built-in IANA tz database the way Linux/Mac do. If a future timestamp anywhere else in the UI needs the same "always show Mario's Miami time, correctly labeled EST/EDT" treatment, reuse this exact pattern rather than trusting a bare `%Z` on whatever tzinfo happens to be attached.
- **A Windows desktop shortcut (`.lnk` from either `.vbs`) is a FIXED pointer to wherever the folder was when it was created — it never "follows" a later-updated copy.** If Mario ever has more than one URTO folder on his PC and the desktop icon + updater icon end up pointing at different ones, updating will look like it silently does nothing (see build order #44) — this isn't an update-logic bug, it's a filesystem-shortcut fact. If this recurs, the fix is consolidating to one folder and re-running both `Create URTO ... Desktop Icon.vbs` scripts from inside it, not touching the update code.
- **`launch_desktop.pyw` self-heals a stale already-running server via `/api/version`** (see build order #44) — if something's already listening on port 5000 but reports a different version than what's actually in `app.py` on disk right now, that's a pre-update process `urto_updater.pyw`'s kill step failed to stop; the launcher kills it itself (same command-line-matched PowerShell approach) rather than just opening a browser tab to whatever's already there. If a future version bump ever needs the comparison to behave differently (e.g. a version format change), update `_installed_version()`'s regex (`APP_VERSION\s*=\s*"([^"]+)"`) and `/api/version` together — they must agree on what "the version" means.
- **`app.py`'s auto-close (`_watchdog`/`/api/shutdown`) always checks `_job_in_progress()` before exiting** (see build order #42) — URTO, unlike Wardrobe, can have a real headed Chromium window mid-FOREWARN-scrape in a background thread when the tab closes or the heartbeat lapses. Never remove that guard or shorten `HEARTBEAT_TIMEOUT` in a way that could fire mid-lookup; a killed process there abandons the scrape with no partial-results file ever written, exactly the kind of silent data loss this whole file warns against elsewhere.
- **`HEARTBEAT_TIMEOUT` must stay generous (180s, not the original 20s)** and `_safe_to_exit()` must keep checking `_request_in_progress()` alongside `_job_in_progress()` (see build order #45) — a background browser tab gets its JS timers throttled hard by the OS/browser (sometimes to once a minute), so a short timeout can force-kill the server mid-upload or mid-save the instant Mario switches away from the tab for a bit, with zero indication anything went wrong beyond "it seems like my document isn't saving." If a future change needs a tighter timeout for some reason, make sure `_request_in_progress()` (the `before_request`/`teardown_request` counter) still guards every real mutation route — it's the more direct protection; the timeout is just the fallback for a truly abandoned tab.
- **Auto-close tracks a SET of active tabs (`_active_tabs`, keyed by each tab's own `tab_id`), never a single global "last heartbeat"** (see build order #48) — with only one global timestamp, closing/reloading ANY one browser tab fired `/api/shutdown` immediately and killed the server out from under a SECOND tab Mario still had open, which then failed with "couldn't reach the server" on its very next click. The server only actually exits once `_active_tabs` is empty. If a future change touches the heartbeat/shutdown wiring, keep the per-tab `tab_id` flowing from `templates/index.html`'s `URTO_TAB_ID` through both `/api/heartbeat` and `/api/shutdown` — collapsing back to a single shared timestamp reintroduces this exact multi-tab bug.
- **A just-launched tab needs `STARTUP_GRACE_SECONDS` (15s, `app.py`) AND an immediate on-load heartbeat (`templates/index.html`'s `sendHeartbeat()` called once before the `setInterval` starts)** to avoid a real race Mario hit (see build order #49): the URTO Updater kills the old server and opens a fresh tab pointing at a new one, and if the OLD tab gets closed in that same instant, its shutdown beacon lands on the NEW server before the new tab's first heartbeat has registered — an empty `_active_tabs` at that split second looks identical to "everyone's actually gone." Don't remove either half of this fix independently — the immediate heartbeat shrinks the race window, and the startup grace period is the backstop for whatever's left of it (a slow browser, a slow first request, etc.).
- **`check_data_health()` compares the live DB against `urto_crm_latest.db`, NOT against every snapshot ever taken** (see build order #50) — comparing against an arbitrary old snapshot would false-positive on every legitimate deletion Mario makes (an old snapshot always has whatever was later deleted). The live mirror is the one file `on_data_changed()` rewrites on every single real mutation, so it should always match the live DB's client count exactly; a live count LOWER than that mirror is real evidence something bypassed the normal save path, not just "data changed since some prior point in time." Don't change this to compare against snapshot history in general — it would make the warning banner fire constantly and Mario would learn to ignore it, which defeats the whole point.
- **`restore_from_snapshot()` reads the chosen backup's bytes into memory BEFORE calling `backup_now()` for the pre-restore safety snapshot** — this order matters and bit us once already (caught during testing, never shipped broken): if the chosen file IS `urto_crm_latest.db`, taking the safety snapshot first would overwrite that exact file with the current (broken) state before ever reading from it, destroying the very backup being restored. Never reorder this — always capture the source bytes first.
- **Every `.modal-overlay` shares the same z-index (100) — stacking order is pure DOM source order, not a real z-index hierarchy** (see build order #52). Opening one modal from inside another (e.g. Follow-up Text from the client detail view) can leave the OLDER one on top if it happens to sit later in the HTML, silently swallowing clicks meant for the new one. `openTextFollowup()` handles this by closing every currently-`.show`n modal before opening itself (`document.querySelectorAll('.modal-overlay.show').forEach(el => el.classList.remove('show'))`) — reuse that same generic pattern for any future modal-launched-from-a-modal flow rather than trying to remember/hardcode which specific modal might be open underneath.
- **`clientForm`'s submit handler is the same "no try/catch around `await fetch()`" bug class flagged in build order #47** (fixed in #52) — Mario hit it for real ("click Save Client and nothing happens"), confirming that warning wasn't hypothetical. If another button anywhere is ever reported as doing nothing on click, grep for `addEventListener('click', async` / `.addEventListener('submit'` and check for a bare `await fetch(...)` with no surrounding try/catch — that pattern still exists in other spots not yet fixed.
- **`add_list_members()` (additive), `remove_list_member()` (single removal), and `set_list_members()` (full replace) are deliberately three separate functions** (see build order #53/#64) — don't collapse them. The Dialer's "Save This List to a Contact List" feature and the CRM's "Manage Members" view both must only ADD or REMOVE the specific client(s) actually being acted on; reusing `set_list_members`'s full-replace semantics there would silently delete every member not present in that one batch/request, which is exactly the kind of silent data loss this whole file warns against elsewhere. `set_list_members` still exists for anything that genuinely computes and sends a complete desired membership set in one shot — nothing currently does since Manage Members moved off it in #64, but don't delete the function.
- **There is no browser event for "a `tel:` call was actually placed or answered"** (see build order #55) — `log_call()`/`last_called_at` uses the same approximation the rest of the Dialer already relies on for dictation and follow-up texts: a click on Call/the phone number/pressing Enter IS the logged call, via `logCallForEntry()`. If a future feature needs "was this call actually completed," that data genuinely doesn't exist anywhere in this stack (no telephony integration, see "Don't do this") — don't try to infer it from timing or `tel:` navigation behavior, it isn't there to infer. **`log_call()` also auto-advances the client's follow-up schedule now** (see build order #65) whenever they were overdue or due-today at the moment of the call — by looping `next_followup_date += interval_days` until the result isn't in the past, not a single hop, so a client missed for several stacked intervals still fully clears in one call. This is intentionally different from `complete_followup()` (the client-detail "Mark Follow-up Complete" button), which still only does one `+interval` hop — don't unify them; `complete_followup()`'s one-hop behavior is what that manual button has always done and nothing has asked to change it.
- **`parseVoiceCommand()` (voice-fill Add Client, build order #56) is keyword/trigger matching, NOT a real AI/NLU model** — don't let its accuracy on the demonstrated example create false confidence about handling arbitrary phrasing. It works by finding trigger-phrase positions in the transcript and slicing the text between consecutive triggers as each field's value, so a genuinely novel phrasing, a missing trigger word, or fields said out of the expected order can misparse (e.g. swallow one field's words into another). This is WHY it never auto-saves: parsed output only pre-fills the normal Add Client form for Mario to review, same pattern as every other fragile-parsing feature here (LLC/trust name extraction, CSV name-order detection). If Mario reports it "got something wrong," don't try to generalize the regex to cover every possible phrasing — that's an unbounded problem this approach was never meant to solve (he was told this upfront); the fallback is the paid Claude-API option he explicitly declined for now, not an ever-growing regex.
- **Every dialer source funnels through `loadDialerList()`** (see build order #59) — this is deliberate and should stay that way: it's the one place that runs `dedupeDialerEntries()` (collapsing repeat phone numbers, e.g. one owner with multiple properties on a lookup-results CSV) and `matchEntriesToClients()` (CRM phone cross-reference). If a future dialer source is added, route it through `loadDialerList()` rather than rendering the dial list directly — bypassing it silently reintroduces both the duplicate-call bug and the missing "In your CRM" matching. **Missed Follow-ups** (build order #65) is the newest example of this pattern — its click handler does nothing but fetch `/api/crm/followups/missed` and hand the results to `loadDialerList()`, same as every other source.
- **A new SQLite table never needs any new backup plumbing** — `_write_backup()`'s instant mirror is a whole-file `shutil.copy2()` of the live DB, not a table-by-table export, so any table added to `init_db()` (e.g. `call_log`, build order #58) is captured automatically the moment a row is written. Only the human-readable exports (`_write_full_data_export()`'s JSON, `_write_crm_contacts_export()`) need an explicit new line added if a new table should appear in THOSE — the raw `.db` mirror/snapshot files never need touching.
- **Any loop that calls `create_client`/`update_client`/`add_note` (or anything else that ends in `on_data_changed()`) more than a handful of times must wrap the loop in `with _deferred_backup():`** (see build order #61) — each of those calls normally triggers a FULL instant backup mirror (whole-DB copy + a re-written CRM Contacts `.txt` per existing client + the full JSON export, to every destination), so a bare loop over N rows does up to N full mirror passes instead of one. This is genuinely slow on a real CRM with existing clients and/or synced OneDrive/Google Drive folders — it's what made the Outlook recurring-follow-up import look permanently hung on Mario's first real run. Both existing bulk-import functions (`import_recurring_followups_csv`, `import_contact_list_file`) and `merge_clients()` (build order #63) already do this; copy the same pattern for any future bulk-write feature (a future "bulk edit clients" tool, a bigger CSV import, etc.) rather than calling the normal single-row functions bare in a loop.
- **A re-run of an import can only prevent NEW duplicates — it can never retroactively merge rows that already exist as separate client records** (see build order #63) — `_find_recurring_import_match()` stops a re-import from creating MORE duplicates going forward, but a client already split into 2+ database rows from an earlier bad run stays split forever unless something actually reassigns/deletes the extra rows. Mario asked for exactly this once ("make it so when I add contacts again it replaces and this is fixed") and re-importing alone genuinely can't deliver it — say so plainly rather than implying a re-import will clean up existing data. `find_duplicate_clients()`/`merge_clients()` is the actual cleanup path: it groups by exact name, reassigns notes/call_log/events/contact_list_members from the losing copies onto the kept one (never deletes real history, just relocates it), and only then deletes the merged-away rows.
- **In this sandbox's headless Chromium, clicking a real `tel:` link with no registered handler leaves the page unable to receive further real clicks** (discovered testing build order #58) — Chromium's native "open in another app?" prompt for an unhandled custom scheme apparently gets stuck open, silently swallowing all subsequent pointer input (confirmed: a capturing `click` listener on `window` stops firing entirely afterward), without ever firing Playwright's `dialog` event (that's for `window.alert/confirm/prompt` only, not this). A JS-triggered `.click()` or a direct function call still works fine — only real Playwright mouse clicks after a real `tel:` navigation attempt are affected. When a test needs to simulate "a call was just placed" and then interact with the page further, call `logCallForEntry(entry)` (or whatever the actual click handler is) directly via `page.evaluate()` instead of clicking the real Call button — this is a test-environment artifact only, not a real app bug, since Mario's actual PC has Phone Link registered as the `tel:` handler.
- **Any timestamp shown to Mario must be 12-hour with AM/PM, never bare 24-hour** (see build order #57) — the footer's "last updated" and `formatLastCalled()` already got this right from the start (`%I:%M %p` / `toLocaleTimeString` with `hour: 'numeric'`, which defaults to 12-hour in the `en-US` locale used everywhere here), but a raw stored value displayed with no reformatting (notes' `"YYYY-MM-DD HH:MM"`, a calendar event's plain `"HH:MM"`) will silently come out 24-hour. Use `formatNoteTime()`/`formatTime12()` for any new spot that displays one of these two raw storage shapes — don't `new Date()`-parse a space-separated (non-`T`) datetime string directly, since that isn't reliably parsed the same way across browsers.
- **Testing `parseVoiceCommand()`/voice-fill in Playwright requires a mocked `SpeechRecognition` that mimics the real "still listening until manually stopped" behavior** — a mock that fires `onresult` + `onend` together on a timer (rather than only firing `onend` when `.stop()` is called) triggers the app's real continuous-listening auto-restart loop (`onend` calls `recognition.start()` again whenever `voiceRecognizing && !voiceManualStop`, mirroring build order #14's dictation), producing a runaway loop that appends the transcript repeatedly and never reaches the "parse it" branch. The working test pattern: `start()` fires `onresult` once and does nothing further; `stop()` is what fires `onend` (after a short delay) — then drive the test with two clicks (start, then stop) exactly like a real user would.
- **Two CRM clients can never share one phone number; a manual calendar event's `list_id` and a Contact List's own recurring schedule are two independent things that must never touch each other** (see build order #54). `crm.find_client_by_phone()` compares phone numbers digits-only with the US country code stripped (`_normalize_phone_key`) so formatting differences never let a real duplicate slip through — `create_client`/`update_client` both call it and raise `DuplicatePhoneError` (→ HTTP 409) before writing anything. This is a DIFFERENT rule from "a client can belong to multiple Contact Lists," which is still fully allowed and unrelated — don't conflate the two if this area changes again. Separately, `create_event`/`update_event`'s `list_id` only exists to let a manual one-off reminder reference a whole Contact List instead of one client; it must never write to `contact_lists.interval_days`/`next_call_date` — those only ever change via `complete_list_round()`. If a future feature touches either of these paths, keep re-verifying both invariants directly (create/update an event, diff the list's schedule fields before/after) rather than assuming — this is exactly the class of "quiet cross-contamination" bug this codebase has hit before with the recurring-followup anchor date (see the manual-events-are-a-separate-table gotcha above).
